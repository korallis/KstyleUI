# KstyleUI_Auras

The player's buffs and debuffs as plain icon rows beside the minimap.

| Field | Value |
| --- | --- |
| Module name | `Auras`: its switch in `Core/Features.lua` and the `name` it registers with `KstyleUI.Modules.Register` |
| Approach | Replace |
| Loads | With the core addon, switched off until the player turns it on |
| Files | `KstyleUI_Auras.toc` lists `Auras.xml`, which loads every Lua file in order, so adding a file never edits the TOC |

## Rules

These come from the [design spec](../docs/superpowers/specs/2026-11-07-kstyleui-design.md). The roadmap's Global Constraints and [AGENTS.md](../AGENTS.md) apply too.

- Auras use the AuraContainer engine (`CustomAuraContainerTemplate`, aura groups and filter strings). Never scan auras by index while `C_Secrets.ShouldAurasBeSecret()` returns true. Aura data turns secret during a boss pull before `InCombatLockdown()` returns true.
- Blizzard frames this module replaces are hidden only through `KstyleUI.Safe.HideBlizzard`.
- At load the module only registers itself with `KstyleUI.Modules.Register`. It creates no frames, registers no events and installs no hooks until `Enable` runs. `test-modules-load.lua` checks the frames.
- Every element it shows registers with `KstyleUI.Layout.Register`, and every setting is declared through `KstyleUI.Options.Register`, so the player can resize and customise everything from the settings window.
- UI comes from `KstyleUI.Widgets`, colours from `KstyleUI.Tokens` and strings from `KstyleUI.L`. Translations live in the core string tables; see Languages in the repository README.
- Build mode: check that an API exists before calling it, check `issecretvalue` before any comparison, fall back to a safer path when the preferred one is unavailable, and log the path taken with `KstyleUI.DevTest.Log`.
- Never read state back from a region inside an engine aura button: visibility, text and size there are secrets on Forever. Keep the wanted state yourself.

## What it shows

Two rows, each a `CustomAuraContainerTemplate` container on the player and its own Layout element, and two optional extra rows built the same way once the player switches them on:

| Element key | Filter | Default place | Default shape |
| --- | --- | --- | --- |
| `auras.buffs` | `HELPFUL`, with the main-hand, off-hand and ranged weapon enchantments first | `TOPRIGHT`, 11.9 left of the minimap element, 1.4 units under the top screen margin (`screenMargin`, 17 units): the picture's 20 px and 32 px on its 2234 px screen | One row of up to 10 square icons of 27.5 units, 3.5 apart, the first aura at the left, the row ending at the element's right edge, an 11-unit timer under each: 306.5 by 41.5 units (27.5 for the icon and a 14-unit timer lane) |
| `auras.debuffs` | `HARMFUL` | `TOPRIGHT`, the same column, 8 under the buffs | the same: 307 by 42 units, its row ending at the same x as the buffs' |
| `auras.extraBuffs` | `HELPFUL`, Blizzard's important buffs by default | Off until **Show this row**; `TOPRIGHT`, right-aligned with the rows above, 12 under the debuffs | One row of six 36-unit icons: 233.5 by 50 units |
| `auras.extraDebuffs` | `HARMFUL`, crowd control by default | Off until **Show this row**; 12 under the extra buff row | the same |

**The picture wins over #209.** #209 shipped "two rows of eight 30-unit icons each, growing left then down". The owner's picture (2026-11-09) draws one row of ten 48 px icons (27.56 units) at a 54 px pitch (31) in listed order, first at the left, with white timers under them, and on 2026-11-09 he ruled "let the picture win its what i want" (LEE-20). So the defaults are now `rows` 1, `columns` 10, `iconSize` 27.5, `spacing` 3.5 and `growth` `RIGHT_DOWN`, the timer 11 units, and every one of them stays a setting (`rows` up to 8, `columns` up to 24): a player who wants two rows, or the row growing left, sets it. A profile that holds its own values keeps them. 27.5 and 3.5 are the picture's 48 px and 6 px on its 2234 px screen (LEE-69; 28 and 3 drew 49 px tiles); migration 16 clears a saved 28 and 3, so a profile left at the old defaults takes the new ones and a size the player chose stays.

The rows stand beside the minimap's left edge, as the owner asked (2026-11-09) and as Blizzard's and Leatrix's setups do. `Core/Setup/Layouts.lua` computes their place from the minimap element's width, so a different map keeps them beside it. The boss column and the spare bar columns stand lower on the screen's right side (#208), so the corner is free at every aspect.

Each tile is a square icon one border inside a one-pixel dark square plate (`black`), as the picture draws it: a plain texture on the tile, so there is no mask, no chamfer and no corner to round. A debuff's dispel plate is the same square under the icon, so the engine's colour shows as a one-pixel ring. No body, no bezel, no shadow. The tile's corners are the module's own; the "+N" cell is the kit's `IconChrome` socket, whose corners and rim the kit draws (it keeps the `edgeInner` and `hostile` accents). The timer sits under the icon in the `timerText` grey-white (#e3e7ec, every stroke of the picture's timers is that one colour) in the Medium `timer` face, 11 units (LEE-94: the picture's timer glyphs are 12 pixels tall and 23 wide on the owner's screen, which this face draws at 11; its soft dark halo is wider than the client's one-pixel shadow can draw), its box 2.5 units under the icon inside the unchanged 14-unit lane (or on its lower edge), and the stack count at the top right inside the tile, as the bible's world-layer text: a one-pixel outline and a soft shadow, no plate (KSTY-60 item 26: the old dark plate poked out of the icon). The engine fills in the icon, the timer, the stack count, the badge, the tooltip and the dispel colour, so secret aura data never reaches KstyleUI's Lua. The engine draws each aura's icon as a secret (`secretwrap`), so no addon code can swap it; the repainted icons reach the tiles anyway, because they ship as a loose-file pack the client loads for every icon ([`docs/icons.md`](../docs/icons.md)), in game and in the renders.

- **Text** goes through `Widgets.ApplyFont`, so the timer and count sizes and their one-pixel shadow land on whole physical pixels in the tile's scale (#210).
- **Timers** use the engine's duration text binding. `short` is the engine's default formatter (`24s`, `8m`, `2h`); `long` and `decimal` are `C_StringUtil` seconds formatters with two units, or tenths under 3 seconds. The timer is `timerText`; a step colour curve turns it `timerExpiring` (the kit's shared expiring colour, 7:1 or more against the outline) under the warning time.
- **Stack badge.** The badge is a `StatusBar` handed to the engine through `SetApplicationBar` with `minApplications = 2` (`Blizzard_AuraContainer/Blizzard_CustomAuraButton.lua`, `ApplyApplicationBar`: `statusBar:SetShown(applications >= minApplications)`), so the engine shows the badge only when the count text it writes through `SetApplicationCount` is not empty. The count font string is the badge's child, so it hides with it. The bar covers the tile and no more, and its own texture is transparent: the badge draws nothing of its own.
- **Debuff type** colours a square plate behind each debuff icon through `AddDispelTypeTexture` with the `PreserveAsset` style, so the engine applies Blizzard's dispel colour and hides it on buffs. A debuff with no type gets the "None" colour. The rim plate sits under it.
- **Right-click cancel** is `SetCancelAuraButtons("RightButtonUp")` on buffs and weapon enchantments. The engine's secure `OnClick` cancels the aura, so it works in combat.
- **Sorting** maps to `AuraContainerSortMethod`: by use (`Expiration`, Blizzard's `AuraUtil.ExpirationAuraCompare`: auras you cast first, then ones you can cast, then the soonest to end, with always-on auras after the timed ones inside each of those; a pet's or another player's buff counts as not yours), time left (`ExpirationOnly`), name (`NameOnly`), order applied (`AuraInstanceIDOnly`), Blizzard's (`Default`) or priority (`UnitFrameDebuff`: boss debuffs, then important ones, then yours first, as Blizzard's unit frames order them), each normal or reversed. Buffs sort by use by default (KSTY-44 row 6) and debuffs by priority.
- **Always-on buffs** sort after the timed buffs of their kind, so most of them reach the end of the row, and fold into its `+N` cell when the row fills. They get no holder of their own: the engine's only duration filter, `candidateFilters.maxDuration`, keeps timed auras and always drops permanent ones, has no inverse (`Blizzard_AuraContainerUtil.lua`, `DoesAuraPassCandidateFilters`), and the filter strings have no duration component, so no group can hold only always-on auras, and addon code cannot read a duration while auras are secret.
- **Aura events are the engine's.** The module registers no `UNIT_AURA`; the engine updates the tiles itself. Weapon enchantments are outside the sort: the engine places them before the aura groups, so they stay at the front of the row. Its own events are coalesced to one pass at the end of the frame: weapon enchantment changes re-apply the buff row once, and the secrecy gate's events queue one restyle.
- **Weapon enchantments** share the buff rows. An active enchantment takes one buff's place (`WEAPON_ENCHANT_CHANGED`, `WEAPON_SLOT_CHANGED`), so the rows never grow past their cap.
- **Many auras.** The rows are the cap: one row of ten buffs and one row of ten debuffs by default (`rows` up to 8, `columns` up to 24). The engine shows the first `rows x columns` of each group by the sort, and the rest read as `+N` on the last cell (the bottom right for a row listed left to right: the engine's flow runs from the container's top left, and the container hangs from the element's right edge): a counting container on `Core/Widgets/Overflow.lua` (`Overflow.New` in `Panel.lua`, one 1-unit element per aura, the labels hung from its foot) that the engine lays out from secure code, so no Lua reads the number and it stays true in a pull. The cell covers the last tile only, so the `+N` tile is exactly the size of the other tiles and level with them (KSTY-60 item 26: it used to cover the timer lane too and stood taller than its row); the covered aura's timer stays under it like every other cell's. It reads the covered aura in its count: 24 buffs over 10 cells read `+15`, and 12 debuffs read `+3`. A row of exactly ten shows all ten, as the owner's picture does.
- **Tracked buffs.** `Tracked.lua` reads the effective layout through `CooldownViewerSettings:GetDataProvider()` only when `IsDirty` is false. `GetDisplayData` contains the player's category overrides, unlike the API's default category set (`Blizzard_CooldownViewer/CooldownViewerSettingsDataProvider.lua`). Base, override and linked spell IDs become the row and count containers' `candidateFilters.excludeSpellIDs`; `AuraContainerUtil.DoesAuraPassCandidateFilters` applies these inside the secure engine. A dirty or unavailable layout, unknown visibility, or a disabled viewer excludes nothing, so uncertainty can duplicate a buff but cannot remove its only display. Data, spell, CVar, `CooldownViewerSettings.OnDataChanged` and `EditMode.Exit` notifications rebuild the filter. **Buffs the Cooldown Manager tracks: Here as well** always keeps every buff. Secret IDs are skipped, never used as table keys.
- **Blizzard's `BuffFrame` and `DebuffFrame`** are hidden through `Safe.HideBlizzard` while the row that replaces each one is built, and come back through `Safe.RestoreBlizzard` when the module turns off, the player turns **Hide Blizzard's buff frames** off, or the gamepad interface is on.
- **Gamepad interface.** While `InputUtil.IsGamepadUIEnabled()` is true, Blizzard's `BuffFrame` and `DebuffFrame` stay on screen and KstyleUI's two rows hide, so the player sees one set of buffs. `INPUT_DEVICE_INTERFACE_TRANSITION` swaps them back and forth through `KstyleUI.Combat.Queue`, so a switch in combat lands when combat ends.

## Why

- **The engine owns aura data.** Aura data turns secret during a boss pull before `InCombatLockdown()` does. `CustomAuraContainerTemplate` reads auras in Blizzard's secure environment and drives the widgets KstyleUI hands it, so the module never calls `C_UnitAuras` and never compares an aura value. It also renders private auras, which Blizzard's `DebuffFrame` shows and a hand-made panel could not.
- **Aura buttons are touched only when the gate is open.** The engine restricts each aura button from tainted code while `C_Secrets.ShouldAurasBeSecret()` is true (`DenyTaintedAccessWhenAurasAreSecret`). Styling happens in `initializeFrame`, before the restriction applies. Any later restyle (a setting, the accent, the scale) runs only out of combat while aura data is not secret; otherwise it waits for `ADDON_RESTRICTION_STATE_CHANGED` or `PLAYER_REGEN_ENABLED`, and the wait is logged. Container-level changes (layout, sort, capacity, and the filters, including Show, Only ones with a duration and the buff spell lists) apply at once, in combat too: the container has no access restriction, so only the button restyles wait.
- **The art lives on a child frame.** Display elements must be descendants of the aura button, and the button forbids untrusted scripts and reparenting. Every KstyleUI region sits on one plain child frame (`skin`) or the badge bar on it, and none of them needs a script.
- **Layout places a holder, not the container.** The container resizes itself, and Layout's mouseover rule hooks `OnEnter` on an element's children four levels deep, which would reach aura buttons. So Layout places an empty `holder` sized to the full footprint, and the container lives on a sibling `host` that covers the holder and mirrors its scale, alpha, strata and visibility through `hooksecurefunc`. The host sits two levels above the holder, so the aura buttons keep the mouse for tooltips and cancelling. The host carries Blizzard's `DisableUntrustedLayoutScriptsTemplate` (`Blizzard_SharedXMLBase/ForbiddenAspectTemplates.xml`), which the engine requires of any frame its containers anchor to; without it the module falls back to a plain frame and logs once.
- **Sizes are elements, not frames.** The flow layout reads `elementWidth` and `elementHeight` from the group layout, so the container lays out correctly even while a button restyle waits behind the gate. Columns become the maximum line size, rows become `maxFrameCount`, and both are snapped to whole pixels in the host's scale.
- **The gamepad needs Blizzard's frames.** Forever's gamepad **View buffs** shortcut (`Blizzard_GamepadActionBars`, `ShortcutsActionBar.lua`) and radial segment (`Blizzard_Gamepad`, `GamepadRadial.lua`) call `BuffFrame:SetGamepadFocus()` and then `DebuffFrame:SetGamepadFocus()`. That check passes on a frame under `Safe`'s hidden parent, because `IsShown()` stays true, so the controller would walk invisible aura buttons. The module reads the style from `InputUtil.IsGamepadUIEnabled`, then `C_InputInterfaceStyle.GetCurrentStyle`; if neither answers, or the answer is secret, it takes the keyboard and mouse path and logs it once.
- **Fallbacks.** Without the AuraContainer engine, or if it refuses a group, that row is not built, Blizzard's frame stays, and the devlog and `/kstyle test` say so. Missing formatters, colour curves, the dispel style enum, `SetApplicationBar` or the Cooldown Manager API fall back to the engine's defaults, a hidden badge or an unfiltered row, with one devlog line each.

## Aura filters

Buffs and debuffs use Only yours and Dispellable by you. Sort by stays beside Reverse order. Spell-ID allow and block lists are offered on nameplates and on your buff row, where the engine matches spell IDs (`CanApplyIdentityCandidateFilters` allows them for helpful auras on you); your own debuffs refuse them, so the debuff row has none. Overflow counters use the same filters as the visible icons.

Buffs and debuffs have independent filters. Missing settings preserve all player buffs and debuffs, the existing sort and the Cooldown Manager exclusion. Weapon enchantments remain separate from spell filters. No saved settings are migrated.

`Tools/regression/test-aura-filters.lua` covers defaults, enabled filters and off at 1920x1080, 2560x1440, 5120x1440 and 3840x2160. `Tools/render/scenes/options_aura_filters.lua` renders the real controls; set `RENDER_AURA_MODULE` to `Auras`.

**Missing, fits** meant a follow-up batch, not a client restriction; round two (2026-11-20) built the last of them. No audited cosmetic control is labelled **Not possible on Forever**: API presence or secrecy is checked at use, and a lack of current implementation is not evidence of impossibility.
