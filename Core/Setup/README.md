# Setup

`KstyleUI.Setup` is the first-run setup: five steps, or six with detected addons, that pick the HUD style, a layout, the modules and addon choices, then apply them and offer a reload. The spec's [Settings and first-run setup](../../docs/superpowers/specs/2026-11-07-kstyleui-design.md#settings-and-first-run-setup) section is binding. `Core/Setup/Setup.xml` loads the files in this order:

| File | What it holds |
| --- | --- |
| `Layouts.lua` | `Setup.Layouts`: the element keys and the Lumen DPS, Tank and Healer layouts: positions, footprints, the module settings each writes and the story slot. See [`element-keys.md`](../../docs/superpowers/plans/element-keys.md). |
| `EditMode.lua` | `Setup.EditMode`: Apply's Edit Mode writer, which puts the objective tracker in the story slot, Blizzard's damage meter on the damage card and Blizzard's tracked buff icon and bar viewers in their slots, plus the durability doll beside the minimap, below its buff row and above the story cards |
| `Looks.lua` | `Setup.Looks`: the one-click Looks, the Keyboard and Gamepad controls and the Interface size choice, named sets of existing settings, and which one the settings match |
| `Setup.lua` | The choices, `Apply`, the story slot's split, the first run, and when the window opens |
| `Integrations.lua` | Live addon discovery, same-job choices and integration lanes |
| `Addons.lua` | The optional Your addons page, using the existing Options settings and skin registry |
| `Window.lua` | The window, built from the widget kit |

Tests: `Tools/regression/test-setup.lua`, `test-setup-first-run.lua`, `test-setup-addons.lua`, `test-setup-editmode.lua` and `test-setup-layouts.lua`.

**Your addons** follows Modules when the client reports enabled supported addons. It offers registry skins and the existing same-job Options settings. Unsupported addons are omitted; if Skins is not loaded, only available same-job choices count. Reopening reads current addon choices; Apply writes them after the layout preset, and Keep my UI discards pending changes.

## When it opens

- At `PLAYER_LOGIN`, when the account switch `Features.account.setupSeen` is off, the setup opens 2 seconds later. The switch is account-wide, so the setup opens once per account, not once per character.
- Applying or closing the setup turns the switch on.
- On the first run, closing the window without Apply (the close button, Escape or **Later**) applies the choice as it stands: DPS and every loaded module unless the player changed them. A skipped setup never leaves an empty screen. The welcome step says so, and **Keep my UI** is the opt-out: it closes the setup and changes nothing.
- A setup opened later with `/kstyle setup` changes nothing when it closes without Apply; it prints how to run it again.
- `/kstyle setup` opens it at any time, on the welcome step with current addon choices and a fresh live addon list.

## The steps

General > Layout pictures in setup defaults on: DPS, Tank and Healer cards show 512x256 HUD renders at 180x90, following the selected HUD style. Off restores the footprint diagram and hover legend. General > Big pictures in setup defaults on: with the layout pictures on, the cards keep their name and note and the footprint diagram's place shows one large 16:9 picture (`Media/Textures/Setup/<Style><Layout>.blp`, 1024x512) of the layout picked or pointed at, in the chosen HUD style; the summary's layout card shows it too. Where the screen is wider than the HUD width (`Scale.Origin()` or `Scale.Band()` above 0), two cards beside it pick the ultrawide arrangement, Centred or Spread, and pointing at one shows its 32:9 picture (`<Style>Centred`, `<Style>Spread`, 1024x256), always of the DPS layout, which the caption says. The pictures are DXT1 BLP2 files, 2.1 MB for all ten. A picture loads only while its step shows: the preview sets its texture only when visible, and turning Big pictures off or closing the window clears it. Off restores the small card pictures. General > One-click Looks defaults on: the HUD style step offers the Looks under the style cards, and the General page offers them under the HUD style. Both show a fourth tab, **Your own**: a disabled status while the settings match a Look, lit when they match none, so the row never changes size. `test-setup-first-run` checks all of it at 1920x1080, 2560x1440, 5120x1440 and 3840x2160 and in every locale. General > Readable setup notes defaults on: 11-unit body notes wrap and respect the reading floor; the two module columns keep each row in line, and the module list scrolls when it needs more room. Off restores the previous small single-line module notes. `test-setup-polish` checks both choices, the 0.65 window scale and picture placement after a text-size change.

The window is a titled `Widgets.Panel` (760 by 540 units, `DIALOG` strata, Escape closes it) that opens at once with the panel's rise, so the window never waits on the client to run a fade. It registers with Layout as `setup.window`, scalable, 40 units above the centre. A `Widgets.Tabs` strip shows five steps, or six with enabled supported addons. A step the player has not reached is disabled, and each page shows at once with no fade: in game, with Motion on, the page fade's alpha animation left parts of a page's first draw out (the Frames card's title, note and edge, a layout card's edge, the Your addons toggles and dropdown).

1. **Welcome.** The logo, a short welcome, the four or five steps ahead, on the first run the note that closing applies the DPS layout with every module on, **Keep my UI** and **Next**.
2. **HUD style.** Two cards side by side on the layout cards' button body, **Medallions** and **Frames**, each with its name, its note and its picture (`HudStyleMedallions`, `HudStyleFrames`, the same pictures the settings window shows) one pad inside the card's sides and foot, so both pictures sit on one line; the picked card wears the `accent` hairline, as on the layout cards. The profile's saved style is picked first, Medallions for a new one. A player whose saved Frames style migration 45 removed in v0.2.12 or v0.2.13 picks it again here; their Frames Layout Mode positions were kept and come back with it. A hint under them says the style changes later at the top of the settings window's General page, and that a change made in combat waits for combat to end. Apply writes the pick to the `HudStyle` section (`Core/HudStyle.lua`), which switches it. Under the hint, **Look** offers Forged, Clean and Readable (see [Looks](#looks)) and shows the Look the settings match; a profile whose settings match none shows **Your own**, which Apply keeps. The row fills only while the step shows, and turning One-click Looks off hides it at once. Under the Look and the Controls, **Interface size** offers Pixel perfect and Game's UI scale (see [Interface size](#interface-size)), always shown, and the window grows by its row while the step shows.
3. **Layout.** One card per layout on the button grade's body, its name and its note, over one large 16:9 preview of the picked layout (the hovered card's while the pointer is on one): a glass panel at the tile chamfer with the drop shadow that draws each element the layout shows at its Lumen footprint (`Layouts.Footprint`, `Layouts.Shown`), names it where its label (or its `short` label) fits the block, and outlines the story slot in the accent and names it (**Story rail**, or **Quests** where that does not fit; round 6, Opus). The elements whose place or presence differs between the layouts (the group frames, the threat and boss cards, your combat text) draw in the accent over the shared hands and rails, so Tank's named threat card and Healer's group frames read at a glance. The legend beside the preview names the outline, the **Story rail**, and says Apply places the quest tracker there through Edit Mode. A click picks the card: an `accent` hairline, the one selection mark setup uses (no glow); the card under the pointer takes the hairline the moment the pointer reaches it, so the outlined card is the one the preview's caption names. DPS is picked first. The preview takes the page's height under the cards, so the step has no empty half.
4. **Modules.** A toggle and a one-line note for each module in `Setup.PICKER`, with **All on** and **All off**. Every module whose addon loaded starts on. A module whose addon did not load is off, disabled and says so. The settings window is not in the list: it loads on demand.
5. **Summary.** The HUD style, the layout, the Look, the controls, the interface size and the modules that will be on and off, then **Apply**. After Apply, the secure **Reload** button and **Later**, and what Edit Mode did (`EditMode.Last()`): the active "KstyleUI <layout>" layout, a write waiting for combat to end, or a refusal with its reason and **Try again** (`Setup.RetryEditMode`), never a drag instruction. When the tracked buffs overflow every arrangement, it names the counts and offers **Open the Cooldown Manager**. Changing a choice afterwards shows **Apply** again.

## Apply

`Setup.Apply(choice)` with `choice = { hudStyle, layout, modules = { [name] = boolean }, look, controls, uiScale, arrangement }`. `look`, `controls`, `uiScale` and `arrangement` are set only by a click on a Look tab, a Controls tab, an Interface size tab or an arrangement card, so the default choice and settings changed while setup is open are left alone. Before the HUD style Apply wears `choice.look` while One-click Looks is on, and writes `Layout.arrangement` from `choice.arrangement` while Big pictures in setup is on; a pick made before its setting was turned off is ignored:

1. For each module in the picker whose addon loaded, `Options.Write(name, "enabled", value)`. Writing through `Options` starts or stops the module through `Modules`, waiting for the end of combat if needed, and fires `SettingChanged`, so an open settings window refreshes.
2. For each element key, the layout's `{ anchor, x, y }`:
   - An element that Layout has registered (`Layout.Get(key)` is not `nil`) moves at once through `Layout.Update(key, position, "setup")`.
   - Every other element, and any that `Layout.Update` refuses, is written into the profile's layout table (`Store.Layout()[key]`). Other fields, such as a size or a shown rule, stay as they are. The modules place these elements after the reload.
3. For each `{ module, key, value }` in `Layouts.Settings(layout)` whose module loaded and has that setting, `Options.Write(module, key, value)`: bars 1 and 2 on in one row with empty tiles shown (LEE-20), bars 3 to 6 off with empty tiles hidden, bars 4 and 5 (the rail's two columns) on with their empty tiles hidden at rest (KSTY-34; a dragged action or Layout Mode shows them), the pet and stance sockets in two rows of five (the stance sockets growing up from their unchanged baseline), the threat card on in Tank only, the menu and bags docked in the readout card, the raid in four groups a row at 77 units wide, and the party and raid row heights (Healer's are larger, with two dispellable debuffs first). The positions carry `Layouts.Sizes(layout)` too: the meters' heights. Settings of a module that did not load are skipped and counted.
4. `Options.Write("Layout", "preset", layout)`, so Layout Mode outlines that layout's story slot.
5. `Options.Write("HudStyle", "style", hudStyle)` when `hudStyle` is a known style, which switches the HUD ([the HUD style statechart](../../docs/statecharts/hud-style.md)); Setup's own `HudStyleChanged` handler does nothing while Apply writes.
6. Out of combat (queued through `Combat.Queue` in combat), `EditMode.Write(layout, Story(layout, guide))` writes the story rail into Edit Mode. See [Edit Mode](#edit-mode).
7. It turns `setupSeen` on and logs the layout, the counts, the HUD style and the modules switched on and off to the devlog.

It returns `false` for an unknown layout, or before the saved data loads.

## Looks

`Setup.Looks.LIST` names three Looks. Each sets the same seven existing settings (Widgets ornaments, card material and panel opacity; Medallions motion and ambient hub effects; the kit's motion and text outline), the Readability text preset and every module text size the text preset writes, every one the Look does not name at its default, so each Look is complete and picking one after another never mixes them:

| Look | What it sets |
| --- | --- |
| Forged | Every value at its default: the look KstyleUI ships with, and the way back |
| Clean | No ornaments, the Glass material at 0.65 opacity, Calm motion for the HUD and the kit, the hub's ambient effects off |
| Readable | The Readable text preset, a soft text shadow, Subtle ornaments, the Slate material at 0.92 opacity, and each module text size raised to the preset's size where it is smaller (a size already larger, such as the 22-unit player name on Frames, stays) |

`Looks.Current()` reads the settings and returns the Look they match, or nil, so a text size of your own reads as Your own; nothing about a Look is saved. `Looks.Apply(name)` writes only values that differ, so picking a Look again puts back every value it owns. `Looks.STATUS` is the list with a disabled Your own tab, shown while a Look matches; `Looks.CUSTOM` enables and lights it when `Current()` is nil. The ornaments and material show on Frames; Medallions draws its own steel, so there the Looks change motion, the hub, panels and text.

### Controls

`Looks.CONTROLS` names two sets of existing Action Bars settings, read and applied by the same code as the Looks (`Looks.Controls()`, `Looks.ApplyControls(name)`):

| Set | What it sets |
| --- | --- |
| Keyboard | Bars 1 and 2 at their defaults: twelve buttons each, no split, the Frames tray on. The way back |
| Gamepad | Bars 1 and 2 at eight buttons each (the controller's two groups of four), each row split in two, and the Frames tray off |

On Medallions the slab keeps its socket size and seats eight sockets either side of the crest: a left and a right group. On Frames the tray goes, so bars 1 and 2 drop the tray column's smaller buttons, and each split row makes a left and a right group of four over four under the unit frames. A set touches no position. General > Keyboard or gamepad bars (on by default) shows the row in setup and on the General page while the Action Bars settings are registered (`Looks.ControlsShown()`); off, or without Action Bars, hides it and leaves the settings alone, and without Action Bars `Looks.Controls()` is nil and `Looks.ApplyControls` refuses. Bigger Medallions sockets are left out: the slab's button size also sizes the hub and the lift of the unit frames above it, which this set does not touch.

### Interface size

`Looks.SIZES` names the two ways KstyleUI can size itself. `Looks.Size()` reads `Appearance.uiScaleGame` and `uiScaleAuto` and returns **Game** while the HUD follows the game's UI scale, **Pixel** on Auto, and nil with a size from the slider, which the row shows as **Your own** and Apply keeps. `Looks.ApplySize(name)`, after the controls, writes `uiScaleGame` (and `uiScaleAuto = true` for Pixel perfect, so it is also the way back from the slider). The same switch, Follow the game's UI scale, sits above Auto on General > Size ([core visuals](../../docs/core-visuals.md#the-pixel-perfect-size)).

## Edit Mode

KstyleUI never calls `SetPoint` on Blizzard's objective tracker, damage meter or Cooldown Manager viewers. Apply writes their places into an Edit Mode layout instead, through the API `Blizzard_APIDocumentationGenerated/EditModeManagerDocumentation.lua` documents on Forever 1.60.1, and Edit Mode moves them:

1. `C_EditMode.GetLayouts()` returns the saved layouts; `EditModePresetLayoutManager:GetCopyOfPresetLayouts()` the presets, which come first in the index Edit Mode counts with (`Blizzard_EditMode/Shared/EditModeManager.lua`, `UpdateLayoutInfo`).
2. The writer finds the account layout named `KstyleUI <layout>`, or makes one: a copy of the active layout, so every other system keeps the player's place, inserted after the last account layout as `MakeNewLayout` does. `IsValidLayoutName` must approve the name, and a full set of account layouts (`Constants.EditModeConsts.EditModeMaxLayoutsPerType`) is never overwritten.
3. In that layout, the `ObjectiveTracker` system hangs its `TOPLEFT` from `UIParent`'s `BOTTOMLEFT`, 16 units right of the quest card column's edge and 34 above its top (`TRACKER_LEFT`, `TRACKER_TOP`), so the tracker skin's glass, which starts 16 left of the tracker and 34 under its top, lands on the quest card's column beside the slot (`Story`). Its Height setting takes Edit Mode's lowest value (400), so a long quest list stays off chat. The guide card stands in the top left corner, so the tracker's place is the same with a guide loaded or not.
4. The `DamageMeter` system sits on the layout's damage card at the card's size (`FrameWidth` and `FrameHeight`, stored less their 200 and 120 minimums, clamped to Edit Mode's 600 and 400), so the meter's Blizzard skin mode, used on restricted clients, sits where the Lumen card would.
5. The `CooldownViewer` system's `BuffIcon` and `BuffBar` entries (`Enum.EditModeCooldownViewerSystemIndices` 3 and 4) are Blizzard's tracked buff viewers, which the Cooldowns module restyles on Forever's automatic path. Blizzard's viewer gives every tracked item a slot (`includeAsLayoutChildWhenHidden`), at least two, each 40 by 40 (a bar 220 by 30) scaled by `IconSize` (stored as (percent - 50) / 10), and ignores `IconLimit` for these two viewers, so the icons are always one row or one column. The writer knows each arrangement's length from the tracked counts (`EditMode.CountTracked(fn)`; `EditMode.Tracked(group)` reads them, six icons and two bars without the module) and tries these places in order, taking the first where every item fits at a readable size (icons 24 root units, bars 18), else at any size down to 50 %, touching no other footprint, the essential and utility slots included, and staying on screen:
   - icons: one row hung from the `cooldowns.buffs` slot's right edge, 14 units above its bottom to reserve the timers, ordered left to right with native direction RIGHT and 3 UIParent units between sockets; else a column beside the focus or right rail, or right of the focus above the target;
   - bars: their independent `cooldowns.bars` slot; else under the target of target, above the focus, beside an already placed dense icon column, or beside the right rail. Each candidate must hold the whole viewer clear of the other elements.
   LEE-20 targets 27.6-root-unit icons. Forever's `EditModeSettingDisplayInfo.lua` exposes only 10% steps, so the nearest legal native size on the owner's default canvas is 28.5 at 60%, not the custom row's exact 27.6. Six native icons span 188.8125 units including gaps, extending 6.2125 left of the 182.6-unit renderer holder into available space; the portrait-side edge stays fixed. The writer checks the actual native bounds against every obstacle and falls back to smaller steps when needed, retaining the engine's 50% minimum. Bars keep a 24-unit cap with a minimum-step exception; `BarWidthScale` comes from the chosen stack width. At 16 icons and six bars, every preset fits at 16:9, 16:10, 21:9 and the owner's 2383 by 1540 screen (`test-setup-editmode.lua`). The writer first protects spare action-bar slots and tries both viewer orders; only if neither arrangement fits does it relax disabled slots. Enabled bar 2 always remains protected. A viewer moves only when every tracked item fits whole and clear. Otherwise it keeps its existing placement and the setup summary names the count and how many would fit, with Cooldown Manager, Try again and Edit Mode as recovery paths.
6. The `RaidWarning` system (boss emotes, boss whispers and raid warnings, which the encounter warnings skin narrows to its lane) goes in the upper band where Blizzard, DBM and BigWigs put warnings, off the nameplates that draw over the characters (round 6, Opus #3): each candidate lane, centred or beside a footprint, starts with its top 15% under the screen's top and sinks under whatever it meets, a rail gap clear; the highest wins, the centred one on a tie, between the rails and above the target. The lanes may cross the quest card and your combat text, both passing text like the warnings (Captain, KSTY-64). Where the group cards and the boss column leave no rail gap, it takes a 4-unit gap at its sides, and where they leave less than the lane (Healer's raid card on a 16:9 root about 1950 units wide), it crosses the group card's right end, never the target, its cast or the boss frames (KSTY-67 item 2). The place is stamped, so a later Apply or a HUD style switch moves warnings Apply placed and leaves warnings you moved. `test-setup-warnings.lua` holds its top in the upper 35% of the screen on every preset and screen.
7. `C_EditMode.SaveLayouts` saves the presets and the saved layouts together, and `C_EditMode.SetActiveLayout` activates the KstyleUI layout.

Offsets are in `UIParent`'s units: root units times the root's effective scale over `UIParent`'s (`EditMode.Factor()`). That ratio changes when the game's UI scale does, and the root's own size changes when Follow the game's UI scale resizes it while the ratio stays put, so Setup's `ScaleChanged` handler restyles the active KstyleUI layout when either moves, as it does for a new layout class or band: the tracker, the damage meter (stamped `meter` since this change; a meter placed by an older Apply has no stamp and stays where it is until setup is applied again), the durability doll, the warnings and the viewers KstyleUI placed keep their place on the screen, and anything you moved stays. A restyle that a change of the game's UI Scale or of the Interface size settings causes (Follow the game's UI scale, Auto or the size slider: `EditMode.Restyle(name, story, true)`) takes a cooldown viewer only in its default place or on its stamp, so an unstamped viewer you moved by hand keeps your place. A HUD width or arrangement change on the same screen resizes the root without changing those, so its restyle takes unstamped viewers as before. A change of the physical screen size (`GetPhysicalScreenSize`) keeps the earlier triggers only (a new layout class, band or warning lane, not the ratio or root size), and that restyle and a HUD style switch still take unstamped viewers as before, so older layouts adapt to a new screen or HUD width as they did. A restyle compares each whole Edit Mode entry before and after, and saves and re-activates the layout only when one actually changed, so the size settings applied at each login do not rewrite it. Every call is protected by `pcall`; a missing `C_EditMode`, a refused name, a full set of layouts or a failed save logs the reason, keeps a player-facing reason for the setup summary, and prints that **Try again** is on the summary.

### Blizzard's essential and utility rows (the fallback, LEE-107)

While the Cooldowns module mirrors the essential and utility rows, Blizzard's `EssentialCooldownViewer` and `UtilityCooldownViewer` are faded and Apply leaves their `CooldownViewer` entries (indices 1 and 2) exactly as the copied layout had them. When the module falls back to them (the restyle chosen, a client without duration objects, or the mirror failing), the viewers show, and in their default places Edit Mode hands them to `BottomManagedFrameContainer` (`Blizzard_CooldownViewer/CooldownViewer.xml:298` and `:309` inherit `BottomManagedFrameTemplate`; `EditModeSystemTemplates.lua:347`), which stacks them at the screen's bottom centre, over KstyleUI's action bars. The module tells Setup which rows fall back (`EditMode.NativeRows(fn)`, `fn(group)` true for `"essential"` or `"utility"`), and the writer places those before the tracked buff viewers, which then keep clear of them:

- Each row stands on its KstyleUI row's baseline: essential centred on `cooldowns.essential`, else growing left from that row's right end, utility from `cooldowns.utility`'s left edge. It is one line of every tracked item (`IconLimit`, which these two viewers use as the line length, `CooldownViewer.lua:2002`), else two, items 50 and 30 UIParent units (`CooldownViewer.xml:20` and `:89`) at the largest `IconSize` step no larger than KstyleUI's icon, down to Edit Mode's 50%, pitched by KstyleUI's gap (`IconPadding` less 4, `CooldownViewer.lua:2015`, never below 0; the grid sets each item's offsets in the item's own scaled units, `GridLayoutUtil.lua:285`, so the gap scales with the icon), with Orientation horizontal and direction right. The whole row must touch no footprint but its own row's, the story slot, the other row or the screen's edge. One that fits nowhere keeps the copied place and the summary names the count and how many would fit.
- A row is placed only while Edit Mode has it in its default place (`isInDefaultPosition`, which a drag clears, `EditModeManager.lua:363`) or exactly where and as KstyleUI last put it in that layout, anchor and the settings it wrote (`KstyleUIDB.account.editModeRows[layout][index]`). A row the player placed or resized stays as they left it; the layout Apply copies is never written.
- A fallback after Apply (`EditMode.PlaceRows()`, which the module calls when a row starts on the restyle) waits a frame so rows that fail together save once, waits for combat to end (`Combat.Queue`), and writes only the active layout and only when it is a `KstyleUI <layout>` one; it saves only when a row moved, then reactivates that layout. In the player's own layout or a preset it saves nothing and logs that Apply places the rows.

`test-setup-editmode-rows.lua` holds both rows clear on every preset at 1280x720 to 5120x1440, 3440x1440, 3840x1080, 3840x2160 and the owner's two Macs, at UI scale 1, 0.64 and the shipped size; checks the all-or-nothing sweep, a working mirror leaving Apply's layout byte for byte unchanged, a row the player moved, KstyleUI's own row re-placed and a dragged one kept, the later fallback in and out of combat, and the module's paths end to end.

| `EditMode.Last() -> { state, name, layout, why, notes }`, `EditMode.Note(note) -> string`, `RetryEditMode() -> boolean` | The last write for the summary: `state` is `none`, `waiting` (combat), `written` or `failed`; `notes` lists `{ group, count, fits }` for tracked viewers no place held. `RetryEditMode` writes the last layout again. |
| `Apply(choice) -> boolean` | See above |
| `Choice()`, `NewChoice()` | The window's current choice, and a fresh one: the saved HUD style, DPS and every available module on |
| `Available(name) -> boolean` | The module's addon loaded and registered. |
| `Go(step)`, `Step()` | Moves to a step, 1 to 5, and reports the current one |

## Why

- The setup never calls a protected function. Modules start through `Modules`, which queues them in combat. The reload is the kit's secure macro button, because `ReloadUI()` is blocked for addons.
- Positions for elements that are not registered yet go straight into the profile's layout table. Most modules are switched on by this same Apply and register only after the reload, and the Layout service reads that table when an element registers.

## The Lumen layouts

DPS, Tank and Healer place every element on the Lumen Rails: two 318-unit rails on the `screenMargin` (17 units, the owner's picture of 2026-11-09) and a shared centre column. The owner's 2026-11-09 ruling, LEE-20 ("let the picture win its what i want"), supersedes the earlier target sigil, common 38-unit tile size and spare-bar stack. `test-setup-layouts.lua` pins the picture geometry for all three presets and seven reference screens while preserving unrelated rail and optional-element slots; `test-setup-collisions.lua` checks the full footprints the modules draw.

- **Left rail:** the raid card at the top, the party at mid-left (centred on the left margin, its top 465 under the top of the 1282.5-unit canvas, where both KSTY-44 mock-ups draw it; KSTY-60 item 6) and chat at the foot, on one left edge: the bare party 259 by 247 (259 by 267 in Healer, its real holder), chat 393 by 186 on the `screenMargin` token (LEE-20: the picture wins over #210's 372). Healer keeps the 318 rail width at the picture's 186 height, because six tracked bars do not fit beside a 393 card on a 2383 by 1540 screen at UI scale 1.

### Why the target shares the player's column

LEE-20 replaces the earlier top sigil with the picture's target directly over the player. Their bars align, while the portraits and target debuffs remain outside the column, so the centre reads as one stack without shrinking the bars to make room for portraits.

A player can still move either frame in Layout Mode. Applying a preset restores the reference column; changing Interface size keeps its bottom offsets rather than lifting a top-anchored sigil.
